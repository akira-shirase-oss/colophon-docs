Each collection now answers GraphQL at `POST /api/v1/projects/{project}/environments/{environment}/collections/{collection}/graphql`, with a body of `{"query", "operationName"?, "variables"?}` and a query of at most 8 KiB. The schema is built for each request from your content types and your role: `entries(where, orderBy, first, after)` returns `nodes`, `pageInfo { endCursor hasNextPage }` and `applied { query queryHash }`, and `entry(id)` returns one draft or `null`. Collections the role can't read are not in the schema.

Why it matters: this is not a second read path. Every call compiles to the same bounded query document that `POST …/entries/query` runs, through the same permission checks, so both answer the same rows with the same `queryHash`. `where` and `orderBy` take only fields the content type marks as indexed, and a refusal arrives as a GraphQL error whose `extensions.code` and `extensions.pointer` are the codes REST uses.

GraphQL is read-only: writes stay on REST with `If-Match` and `Idempotency-Key`, and public reads stay on `/content/v1`.

```graphql
{
  entries(where: { section: { eq: "News" } }, orderBy: [{ field: rating, dir: DESC }], first: 10) {
    nodes { id title author { title } }
    pageInfo { endCursor hasNextPage }
  }
}
```
